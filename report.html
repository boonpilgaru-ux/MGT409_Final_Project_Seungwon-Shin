tee:dentity02 · MOTIVATION

2. Motivation

Turning personal taste into a shirt is a translation problem

The project starts with a product hypothesis: people may know what they like without knowing how to search for a shirt that expresses it.

Who might have this problem

A person choosing a graphic tee for themselves may be trying to signal a place, music or film reference, a sense of humor, or a visual style. The starting point is often a loose feeling rather than a retailer keyword. A shopper has to translate that feeling into search terms, judge whether a product actually matches it, and then decide whether a custom-print service is worth the effort.

Tee:dentity is aimed at that exploratory moment: someone who wants a shirt to feel personal but has not yet decided what graphic, wording, color, or fit should go on it. The country-aware A/B game is a lightweight way to turn examples into stated preferences. It is not a personality diagnosis or a validated psychological instrument.

How the task is handled today

Common alternatives split the work. A shopper can browse a marketplace, enter a few keywords, ask a general shopping assistant for options, or open a custom apparel designer and supply their own art. Those are useful approaches, but each asks the shopper to bring the brief. Tee:dentity tries to build that brief first and keep discovery and customization in the same flow.

What the app measures.
The live smoke completed 10 questions, a profile, a retailer search, design generation, revision, and a demo order path. It records model token totals and API-call timings.
What it does not measure.
No interview notes, participant feedback, control group, shopping-time baseline, purchase conversion, willingness to pay, or before-and-after relevance score are present.

Why the problem matters—and what remains a hypothesis

Clothing is visible and personal, so the project treats the act of choosing a design as a small self-expression task. The practical stakes here are convenience and fit of recommendations, not health or financial outcomes. The app may reduce the blank-page problem by offering a starting point; there is no measured evidence yet that it saves time or reduces frustration. Establishing whether people actually want this guided flow is a first research task, not a conclusion of this report.

Source basis: project prompts in AI_prompts.md, current interface and code, and the dated live smoke evidence in the repository.

What the product does differently in the prototype

The first half of the experience asks for choices across food, culture, mood, and ideas. Those answers feed a profile containing an archetype, traits, palette, and T-shirt brief. The design choice has a trade-off: a guided intake can make recommendations easier to start, but it constrains what the user can express. People who prefer direct search, already know their art, or want a production checkout may prefer the existing alternatives.

tee:dentity04 · THE AGENTS

4. The agents · architecture

One app workflow calls several specialist model tasks

“Agent” is a useful shorthand for the task roles, but the code does not run independent agents that plan or delegate to one another.

FastAPI routes and session-state checks control the order. Each model call receives a specific task and expected output. Most use structured JSON; the retailer-search step uses the hosted web-search tool. Multiple searches and design concepts can run concurrently inside a defined step, but there is no general-purpose planner, agent framework, or agent-to-agent handoff.

Person chooses a country and answers the 10-round A/B game
↓
Question task · gpt-6-lunaOne short prompt and two options per round; Wikipedia / Wikimedia image discovery and one photo-judge task.
Optional context task · gpt-6-lunaSafe URL fetch or PDF/DOCX/TXT/MD extraction; untrusted material is summarized as data.
Profile task · gpt-6-lunaAnswer history plus accepted context becomes an archetype, traits, palette, and shirt brief.
Shop task · gpt-6-lunaThree concurrent hosted web searches; direct HTTP checks screen product pages and photos.
Design task · gpt-6-lunaThree SVG concepts and optional revision; a local allowlist sanitizer checks the result.
Quote and demo order · deterministic codePrice formula, order snapshot, share link, and request record; no charge or fulfillment.
↓
React + Vite interface presents the profile, retailer links, design preview, and demo order brief.

This diagram summarizes current route and service code. Optional context can be skipped. The model name is fixed in configuration for every role.

How the work is delegated

The user’s choices and session state select the next API operation. The backend validates state and limits before calling a module. Within the shop step, local / indie / global searches can run in parallel. Within the studio step, three concepts can run in parallel. The route waits for or streams back the step result; the model does not choose which backend tool to call in an open-ended loop.

After the 10 answers, the UI can begin shop and design prefetching while the person reads the profile. That improves responsiveness but creates requests before the person opens those pages. The report separates this observed prefetch behavior from the original scripted smoke measurement.

Code basis: backend/app/routes.py, quiz.py, context.py, profile.py, shop.py, design.py, config.py, and frontend/src.

4. The agents · responsibilities

Task roles share one course model and a small set of tools

RoleModel actionTools and checks
Question writerGenerates one country-aware A/B question at a time and consumes prior answers.Portkey chat completion with a JSON schema; Wikipedia article / Wikimedia Commons image lookup; Luna photo judgment.
Context summarizerCompresses notes, public web pages, or parsed files into a short signal summary.Bounded HTTP fetch, public-IP and redirect checks, isolated PDF/DOCX parser, Portkey chat text; untrusted-data delimiters.
Profile synthesizerTurns answers and permitted context into the profile and downstream design brief.Portkey structured JSON response; semantic checks and bounded prompts.
Shirt researcherLooks for buyable product pages associated with the profile and selected answers.Portkey Responses API with hosted web_search; direct page / image HTTP checks; product-title and source evidence labels.
Design generatorProduces three SVG concepts and can revise a chosen concept from user feedback.Portkey chat response; local XML/SVG allowlist sanitizer and palette/spec extraction.
Order serviceNo model. Prices specifications, stores a snapshot, and records a demo request.Deterministic price formula, SQLite, order link, and downloadable sanitized SVG.

Model choice

All configured roles—including the backup search and JSON-repair role—are hard-set to gpt-6-luna through the Portkey-compatible API. The health endpoint reported that model for each role during the smoke run. The reason is course-key compliance and a consistent model boundary, not a benchmark claim that Luna is best for every task. The code does not switch to other models.

Important observability limit

The app writes aggregate token totals and a request count per session. It does not preserve each prompt and response, and it does not produce a per-agent request breakdown or a durable event trace. This protects prompt text from being stored in the usage table and keeps the report grounded in the evidence that exists; it also means a screenshot of internal agent-by-agent execution could not be reconstructed from the application logs.

What “agent actions” means here. The actions listed above are code-defined roles and tools used by the current app. They are not a claim about hidden model reasoning, autonomous goals, or independent agent identities.

4. The agents · one real run

A synthetic South Korea run reached the demo order path

This example comes from the real Portkey-backed smoke run on October 26, 2026. Its context text and URL were synthetic; it was not a participant study.

  1. Start and play. The API returned a South Korea session and all 10 quiz rounds. Fourteen of 20 option cards had photos; six of 10 rounds included native-script sublabels. Median answer latency was 3.3 seconds, maximum 4.7 seconds; 1 of 9 non-final answers was under 3 seconds.
  2. Add optional context and make a profile. The synthetic note and public Seoul Wikipedia URL were accepted. The profile was “The Euljiro Night-Ride Collector,” with 7 traits and 5 palette colors.
  3. Search shirts. Ten suggestions returned: 2 local, 3 global, 5 independent; 8 of 10 had images. The app labeled answer matches only when product details supported one.
  4. Design and request a quote. Three designs and one requested revision completed. A 12-shirt quote totaled $280.80; a demo request and print-ready SVG succeeded. No payment or shirt production occurred.

Assumptions. One completed journey per user per month; same answer count, context length, model, retries, and shop results as this one synthetic run; linear cost; no additional system cost. Actual usage may be higher or lower. The measured 43-request session after browser evidence work cost $0.0645748, but includes repeated Profile capture work and is not used as a clean per-user run.

Cost controls in the code

  • The flow is capped at 10 quiz rounds. Structured responses, bounded context, and concise summaries constrain many model outputs.
  • Shop searches have time budgets and use low search-context size. Candidate pages and images have fetch limits, redirect limits, and timeouts.
  • Design generation limits concept counts and sanitizes output before storage. Concurrent requests for an already-running shop or design job can be joined.
  • Model endpoints use a per-IP token bucket and return HTTP 429 when depleted. This slows one client; it is not a monthly spend cap across all users.
  • The selected model is fixed to the course-approved Luna model. Portkey usage is logged as aggregate tokens, not prompt/response text.

Does lower cost reduce quality?

No controlled quality-versus-cost experiment was run. Low search context, response limits, and concise summaries might omit useful details; the log contains no comparison that quantifies this effect. The force-refresh header prevents the app from returning a stale cached answer as a new result. Cached-input token pricing still appears in provider usage.

The projection arithmetic is reproducible from the scripted run’s recorded total. It omits fees whose rates were not measured; it should not be read as a full cost-to-serve estimate.

tee:dentity06 · SAFETY · RISKS

6. Safety

The main risks come from the material the app reads and creates

Tee:dentity accepts free text, public URLs, and documents, calls outside services, and displays model-generated SVGs. These risks are more relevant than abstract “AI safety” claims.

Prompt injectionNotes, uploaded essays, and linked pages can contain instructions aimed at the model rather than facts about the person.
Incorrect or overconfident resultsA model can misread a preference, invent product details, or produce a shirt concept that looks plausible but is wrong.
Unsafe URL fetchingA hostile URL, redirect, or DNS change could try to reach a local service or cloud metadata endpoint.
Unsafe generated markupAn SVG could carry script, event handlers, external links, or expensive structure if rendered without filtering.
Token or search abuseA loop or repeated public traffic could create model and search charges. Per-IP limits do not cap total spending.
Personal dataUsers can share notes, social links, essays, or resumes. The app stores session data locally and sends selected content to the model service for processing.

What these risks mean in practice

Uploaded or linked context can reveal personal details and may be untrusted. The API’s SQLite store retains session state; idle sessions default to 30-day retention, and “Start over” deletes that session’s state and usage totals. There is no sign-in, account export, or production privacy program in this student prototype. The Portkey key itself is server-side environment configuration and the health endpoint reports only whether it is set.

Retailer pages and web-search results can change after the model sees them. A “why it fits” explanation is an interpretation, not a fact about the shopper. The app records which answer match source it found, but the price and availability shown by a retailer may later change. The order flow is a demo and is not a safe or complete payment system because it takes no payment at all.

Spending boundary. Per-client rate limits, retries, and timeouts reduce some abuse and hung requests. There is no global budget monitor or automatic shutdown when the Portkey key reaches a monthly amount. Public deployment would need provider-side spend limits and monitoring.

Remaining risk

Prompt wrappers are a useful boundary, not a guarantee that the model cannot be influenced. A person may also supply a URL with misleading information, and a generated profile may state an unsupported interpretation. Product data still depends on search freshness. The strongest next test would use a consented test session with an adversarial page, verify what text reaches each model, and inspect the resulting output without putting real personal data in the test.

How value should be tested next

Ask participants to find a shirt for a stated occasion using their usual method and using Tee:dentity. Measure time, confidence, and independent ratings of whether each result reflects their expressed taste. Give participants a way to reject or correct the generated profile. Record the country, device, and task without collecting unnecessary personal data. A small usability round could expose friction; a later comparison would be needed before attributing any improvement to the app.

tee:dentity08 · LIMITS + NEXT STEPS

8. Limits + next steps

A working prototype still needs user evidence and operating controls

Current limits

  • Only five markets are configured: United States, South Korea, Japan, China, and India.
  • Profiles reflect one set of answers and model interpretation; the traits are not validated measures of personality.
  • Retail search can return unavailable, stale, or weakly matched products. Inventory and prices live on external pages.
  • The custom order is a quote/demo snapshot. There is no payment, print fulfillment, shipping, or support operation.
  • The app uses one course model for every role; there are no agent-level usage counters or live execution trace.
  • SQLite and anonymous session IDs suit a local class project, not a multi-tenant production service.
  • Per-IP rate limits do not cap total provider spending. Search-provider fees are not part of the token estimate.
  • There is no real-user feedback, controlled impact study, or public live deployment.

What I would build with one more month

  1. Run moderated think-aloud sessions with people from the five initial markets; log completion, confusing questions, and preferred outputs.
  2. Compare the shop list against each participant’s own shortlist with blinded relevance ratings and record the method.
  3. Measure task time against the participant’s usual shopping approach before claiming time savings.
  4. Add per-role token and latency records, a provider budget alarm, and a hard global spend ceiling.
  5. Review retention, deletion, key management, and isolation before deploying outside a local classroom demo.
  6. Improve search freshness checks, clearer “price may change” treatment, localization review, and recovery when a role fails.
  7. Only then test whether a real print partner can fulfill the custom design flow.
Evidence still to collect personally

Real-user feedback and task observations; a controlled relevance/time comparison; and, if the instructor expects a screen recording of internal agent actions, a trace capture from an instrumented run. The current app and saved smoke record expose aggregate usage, not per-agent logs.

Tee:dentity demonstrates a connected AI-assisted workflow. Whether that workflow helps someone choose a shirt is the next question to test.
